XFL CSMS - how to run
=====================

Deploying to a server (IIS): see docs/DEPLOYMENT.md. Release build: ./scripts/publish.sh

Requirements
------------
- Visual Studio 2022 with the "ASP.NET and web development" workload and the .NET 6 SDK/runtime
- SQL Server (Express is fine)

1. Database
-----------
Option A - use the supplied data (CSMS.bak)
   CSMS.bak was taken on SQL Server 2022 (version 16). SQL Server can only restore a backup on the
   same or a newer version, so this needs SQL Server 2022 or later.
   SSMS > Databases > Restore Database > Device > CSMS.bak > restore as "CSMS".
   Nothing else to do: the migrations are already recorded in that database.

Option B - start with an empty database (also the way to go on SQL Server 2019)
   Do nothing. On first start the application creates the "CSMS" database and all tables by itself
   and, because the database has no users yet, creates a first administrator:
        user name: admin        password: Admin@12345
   (values come from "SeedAdmin" in appsettings.Development.json; change the password after signing in).
   That administrator can then create brokerage houses and branches, which registration needs.

   Sample data (Development only): with "SeedDemoData": true in appsettings.Development.json, a database
   that has no tickets yet also gets 3 brokerage houses with branches, support types/categories/
   sub-categories/affected sections, 10 tickets in every status, to-dos and one account per role
   (password Demo@12345, from "SeedDemoPassword"):
        manager                         Support Manager
        engineer1, engineer2            Support Engineer
        maker.alpha, maker.alpha2       Maker, Alpha Securities Limited
        maker.beta                      Maker, Beta Capital Limited
        maker.inactive                  disabled account (sign-in is refused)
   A database that already has tickets (e.g. the restored CSMS.bak) is never touched.
   Set "SeedDemoData": false to switch it off.

2. Connection string
--------------------
XFLCSMS/appsettings.json > ConnectionStrings > DefaultConnection
   default:  Server=.\SQLEXPRESS;Database=CSMS;Trusted_Connection=True;...
   - "."            = this computer
   - "\SQLEXPRESS"  = instance name. For a default (unnamed) SQL Server instance use  Server=.
(The connection string is no longer hard-coded in Data/DataContext.cs.)

3. Run
------
Open XFLCSMS.sln and press F5 (profile "XFLCSMS" -> https://localhost:7044 or http://localhost:5100).
Do NOT run Add-Migration: the model and the migrations are in sync. Update-Database is not needed either
(the application applies pending migrations at start-up; set "Database": { "AutoMigrate": false } in
appsettings.json to switch that off).

4. E-mail
---------
Registration and "forgot password" send a token by e-mail using EmailHost / EmailPort / EmailUsername /
EmailPassword. The password is NOT in appsettings.json any more (that file is in the public repository).
Put it in XFLCSMS/appsettings.Local.json (git ignores this file), for example from Git Bash:

   cat > /e/XFL-CSMS-main/XFL-CSMS-main/XFLCSMS/appsettings.Local.json <<'JSON'
   { "EmailPassword": "your-new-gmail-app-password" }
   JSON

or set the environment variable EmailPassword. Without it the app starts and works, but no e-mail is sent
(the log says so at start-up). If the mail cannot be sent the user sees a message instead of an error page,
and a registration whose mail failed is rolled back.

See FIXES.md for the list of what was changed.

5. Client ratings and Engineer Scorecard
----------------------------------------
- When XFL staff close a ticket, the client who raised it gets an e-mail and can rate it for 14 days, change the
  rating for 48 hours, and reopen the ticket if the problem is not solved (Maker > ticket page). The form asks:
  overall stars (CSAT), speed / communication / quality / professionalism / knowledge (1-5), fully solved?,
  solved the first time? (FCR), effort to get it solved (CES 1-5), likelihood to recommend (NPS 0-10),
  quick tags (praise / problems) and a comment.
- A rating of 1-2 stars or "not solved" is e-mailed to every Admin and Support Manager and must be followed up
  within 48 hours (overdue badge). Management can reply to the client (shown on the client's ticket page and
  e-mailed), and can leave a rating out of the scorecard with a recorded reason (fairness).
- Ratings are visible ONLY to Admin and Support Manager: menu "Service Feedback" (KPI tiles, trend, star
  distribution, NPS, dimensions, tags, per engineer table, CSV) and a "Client Rating" panel on their ticket page.
  Support Engineers never see them.
- Menu "Engineer Scorecard" ranks Support Engineers per month: score 0-100 from client rating 25, SLA met 20,
  resolution time 15, volume 10, reopens 10, first-contact resolution 10, first response 5, overdue backlog 5.
  It shows team KPI tiles, a podium, a leaderboard chart of what each score is made of and 6-month trends.
  Click an engineer for the Engineer Profile: rank, KPIs, score and quality trends, strengths and gaps against
  the team (radar), coaching summary, service dimensions and the latest feedback.
- An engineer is ranked with at least 5 closed tickets in the month (no rating needed: without ratings the
  client-rating part counts as average). A month is frozen on the 3rd of the next month and the top engineer who
  passes the award rules (3+ ratings, adjusted rating 4.0+, CSAT 80%+, SLA met 85%+, no unreviewed 1-star
  rating) is nominated "Best Support Engineer of the Month"; a manager confirms or picks another engineer with a
  reason (confirmed automatically after 5 days).
- SLA targets are in MINUTES per priority: Admin > SLA Targets (default High 60 / 480, Medium 240 / 2880,
  Low 1440 / 7200). The migration PerformanceKpisAndSlaMinutes converts existing hour values to minutes.
- Weights, minimums and award rules: appsettings.json > "Scorecard".
- Charts follow the light / dark theme switch.

6. Install as an app (PC and phone)
-----------------------------------
XFL CSMS is an installable web app (PWA): it gets its own window, a start-menu / home-screen icon, and an
"offline" page when the network drops. Tickets are always loaded live from the server.
- PC (Chrome or Edge): open the app, then click "Install app" in the top bar (or the install icon in the
  address bar). Works on http://localhost / http://127.0.0.1 without HTTPS.
- Android (Chrome): open the HTTPS address, then "Install app" (or menu > Install app / Add to Home screen).
- iPhone / iPad (Safari): open the HTTPS address, tap Share > Add to Home Screen.
Phones need HTTPS (browsers only install apps from https:// addresses, localhost excepted). Ways to get it:
  a) quick test from a phone: a Cloudflare tunnel gives a temporary https:// address for the app running on
     this PC (no router or certificate setup). In Git Bash:
        winget install --id Cloudflare.cloudflared
        cloudflared tunnel --url http://127.0.0.1:5200
     and open the https://....trycloudflare.com address it prints on the phone. Anyone with that address can
     reach the sign-in page while the tunnel runs; close it with Ctrl+C.
  b) for real use: publish to IIS on a server with a domain name and a trusted certificate (for example a free
     Let's Encrypt certificate installed with win-acme), and open https://your-domain on PCs and phones.
The app reads X-Forwarded-Proto from a proxy / tunnel, so links in e-mails use https:// behind one.

7. Ticket lists, reports and charts
-----------------------------------
- Every ticket list (All / Unassigned / Closed / Assigned to me / My tickets) and the Ticket Reports page of
  every role use one page: filters (period or dates on created / closed / updated, brokerage house, branch,
  product, status, priority, support type, category, sub-category, affected section, engineer, SLA state,
  open longer than N days, free text), KPI tiles and a detailed table with 28 columns: "Columns" shows / hides
  fields (remembered in the browser), the row under the headings searches one column, + opens every field of
  a ticket, and Copy / CSV / Excel / PDF / Print export what is shown.
- The report adds charts (created vs closed trend, status, priority with SLA met %, backlog by age, product,
  house, engineer, category, busy hours) and breakdown tables per house, branch, product, engineer, category,
  support type and priority, each exportable.
- Dashboards show the same KPIs and charts for 7 / 30 / 90 days or 12 months.
- Scope: Admin and Support Manager see every ticket; a Support Engineer's report covers tickets assigned to
  or closed by him (his lists show every ticket, as before); a Maker sees only the tickets he raised.

8. Health check
---------------
http://<server>/healthz answers "Healthy" (200) when the app runs and the database answers, 503 otherwise:
point IIS / an uptime monitor at it.

9. Earlier versions side by side
--------------------------------
Two earlier versions are kept for good (commits on main, pinned in scripts/run-original.sh):
   v1-original      49b1f77  first stable version (before the 2026 rework: ratings, notifications, new layout)
   vendor-original  c60ff0b  the code exactly as handed over by the vendor
To also see them as tags on GitHub (optional):
   git tag v1-original 49b1f77 && git tag vendor-original c60ff0b && git push origin v1-original vendor-original
Run them from Git Bash in this folder, next to the current version (no second clone: the tag is exported
into the git-ignored folder .original/ and built there, so this checkout is not touched):
   scripts/run-current.sh                   current version  http://localhost:5200  database CSMS_Old
   scripts/run-original.sh                  v1-original      http://localhost:5201  database CSMS_Original
   scripts/run-original.sh vendor-original  vendor code      http://localhost:5202  database CSMS_Original
   scripts/run-both.sh                      5200 and 5201 together, Ctrl+C stops both
CSMS_DB=..., CSMS_SERVER=..., CSMS_PORT=... change the database, SQL Server or port, e.g.
   CSMS_DB=CSMS_Old scripts/run-original.sh
- On an empty CSMS_Original, v1-original creates the tables and the admin / Admin@12345 account. The vendor
  code creates nothing: run v1-original once first.
- The old versions can open CSMS_Old (newer changes only added tables and columns), but whatever you do in
  them is saved there. Accounts that have signed in to the current version use the newer password hashing
  and cannot sign in to the old versions.
- The old versions cannot send e-mail when started by these scripts.

10. CI
------
GitHub Actions (.github/workflows/ci.yml) builds every push to main and every pull request, runs the tests
(none yet) and keeps the published site as a download (Actions > the run > Artifacts) for 30 days. It also
builds v1-original so the frozen copy stays buildable.
